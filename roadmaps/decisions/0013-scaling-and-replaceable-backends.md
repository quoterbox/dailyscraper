# 0013. Производительность, сменные бэкенды и работа на нескольких машинах

Статус: принято (2026-10-28), уточняет [0002](0002-sync-dispatcher-and-process-slots.md)
и [0012](0012-transports-isolation-and-sync-core.md)

## Контекст

- Фреймворк рассчитан на нагрузку от десятков до тысячи одновременных HTTP-потоков,
  каждый на своей прокси, и на десятки браузеров на машину.
- Одна машина ограничивает число браузеров памятью; для сотен браузеров нужно
  несколько машин с общей очередью.
- SQLite и локальные файлы подходят одной машине; для нескольких машин нужны
  PostgreSQL, Redis и общее хранилище файлов. Переход не должен требовать
  переписывания исполнителей, Dispatcher и сервисов.
- Отказ одного процесса или машины не должен терять подтверждённые данные и
  задачи.

## Решение

### Нагрузка на одной машине

- **Дорожки HTTP-слота.** HTTP-слот выполняет до N задач одновременно (дорожки),
  у каждой своя прокси. Дорожки — потоки с синхронным кодом; async внутри
  HTTP-слота включается только по результатам замеров.
- **Лимит одновременности на парсер.** `max_parallel` для парсера (и при
  необходимости для сайта) соблюдает Dispatcher вместе с лимитами хоста.
- **Пакетные отметки.** Слот сообщает о сохранённых строках пачками (по числу
  строк или по времени), а не на каждую строку; строки лежат в partition-файлах,
  в хранилище попадают только отметки. Нагрузка на хранилище определяется числом
  пачек, а не строк.
- **Замеры.** У этапа HTTP-транспорта есть нагрузочный тест на 100 одновременных
  дорожек и замер на 1000 против локального тестового сервера.

### Сменные бэкенды

- **Порты и адаптеры.** Всё, что хранит общее состояние, используется только
  через интерфейсы: очередь задач и попыток, run и команды, leases, health
  прокси, события, хранилище артефактов (partitions, снимки ошибок, экспорт).
  Первая реализация — SQLite и локальная файловая система; PostgreSQL, Redis и
  S3-совместимое хранилище добавляются как адаптеры без изменения кода над
  интерфейсами.
- **Контрактные тесты бэкендов.** Один набор тестов поведения проверяет каждую
  реализацию интерфейса. Новый бэкенд готов, когда проходит этот набор.
- **Без особенностей SQLite в семантике.** Захват задачи — атомарная операция
  «взять одну доступную и пометить», которая в PostgreSQL ложится на
  `SELECT … FOR UPDATE SKIP LOCKED`. Время для leases и `not_before` берётся из
  одного источника — часов хранилища, а не процесса. Идентификаторы — строковые,
  без зависимости от автоинкремента.
- **Идемпотентность.** Повторная доставка сообщения слота или повтор операции
  после сбоя не меняют результат: попытки, пачки строк и команды имеют
  собственные идентификаторы.

### Несколько машин

- **Роли.** Координатор (очередь, ворота, выбор прокси, retry, финализация run) и
  агент хоста (BrowserManager и слоты одной машины, лимиты этой машины). На одной
  машине обе роли работают в одном родительском процессе — это текущий режим.
- **Протокол слота сериализуемый.** Сообщения «родитель ↔ слот» — версионируемые
  модели данных, которые сериализуются в JSON, а не произвольные Python-объекты
  через pickle. Тот же протокол может идти по сети между координатором и агентом.
- **Идентичность.** Attempts, leases, слоты и события несут `host_id`. Lease
  истекает без heartbeat; задачи упавшей машины возвращаются в очередь.
- **Принцип одного писателя** обобщается: в общее хранилище пишут только
  координатор и агенты через транзакции; слоты не пишут в него никогда.
- Сама работа на нескольких машинах — отдельный этап после паритета
  эксплуатации; до него фундамент выдерживается без реализации второй машины.

## Последствия

- `storage/` строится как набор интерфейсов и SQLite-адаптер; модули выше не
  импортируют `sqlite3`.
- Протокол слота и события описываются схемами с версией с первого дня.
- Dispatcher использует интерфейсы очереди и аллокатора прокси и не знает,
  локальные они или общие.
- Нагрузочные цели проверяются тестами, а не оценками.

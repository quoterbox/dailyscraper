# 0019. Ворота, discovery и probe

Статус: принято (2026-10-29), уточняет [0011](0011-page-execution-contract.md) и
[0017](0017-proxies.md)

## Контекст

В MVP перед парсингом шёл общий барьер: network check, мини-прогон каждого
парсера через прокси (scraper health), поиск последней страницы каждой ссылки
(page discovery), затем раскладка страниц по jobs (`pages_per_job`). Один
медленный парсер держал все остальные. В dailyscraper задачи уже идут через
общую очередь и слоты; эти шаги нужно встроить в неё же, без барьера.

## Решение

- **Типы задач.** К `list` и `detail` добавлены `probe` и `discover`. Это
  обычные задачи в обычных слотах: прокси, лимиты, повтор на другой прокси,
  сторож и отмена работают для них так же.
- **Ворота на парсер.** Если у пакета включён `health_check`, планировщик
  ставит одну задачу `probe`, а остальные задачи парсера ждут, пока ворота не
  откроются. Парсер без проверки открыт сразу; ворота одного парсера не держат
  другие.
- **Probe** — мини-прогон без записи результата: первая страница каталога
  (или `health_check.urls`, или первые строки входа для detail) через прокси
  слота; успешен, если собрано не меньше `min_items` элементов со всеми
  `required_fields`. Блок, капча и сетевые ошибки — повтор на другой прокси;
  целая страница без элементов или без обязательных полей — категория
  `invalid_content`, без повторов: сломаны селекторы, прокси ни при чём.
  Провал после всех попыток: при `blocking: true` ворота закрываются и задачи
  парсера отменяются, иначе открываются с предупреждением.
- **Discovery** — алгоритм MVP: страница `start_page`, затем шаг удваивается до
  первой пустой страницы, затем бинарный поиск между последней непустой и
  первой пустой; пустая страница подтверждается `empty_confirmations` раз,
  неопределённая повторяется `unknown_retries` раз; «только рекомендации»
  распознаются по `empty_when_no_items_text_markers`. Нужен
  `pagination.url_template`. Ссылки с одинаковым адресом без параметров
  страницы и сортировки проверяются один раз.
- **Страницы поиска не открываются дважды.** Каталоги часто короче трёх
  страниц, и поиск открывает их все. Товары каждой страницы, найденной с
  товарами, сохраняются прямо в задаче `discover` (`save_items`, по умолчанию
  включено; для пакетов со страницей деталей — нет, иначе поиск длился бы как
  вся ссылка). Страница, повторяющая уже сохранённую, считается пустой: так
  магазины отвечают на номер за последней страницей. Сохранённые страницы
  берутся из той попытки, строки которой попадают в результат.
- **Повторы страниц.** Одно правило для всех мест, где страницы сравниваются:
  `page_scrapers/repeats.py` сравнивает ключи товаров страницы с предыдущей
  страницей или со всеми прочитанными. Ключ — хук пакета `item_key`, иначе
  `pagination.repeats.key_fields`, иначе ссылка на товар, иначе содержимое.
  Страница — повтор, если совпали все товары (`match: all`, по умолчанию),
  хотя бы один (`any`, поведение MVP без `stop_if_all_items_the_same`) или
  доля `min_share` (`share`). Реакция зависит от того, как открыта страница:
  открытую по адресу каталог открывает заново, после клика — ждёт, пока сайт
  переключится; после `confirmations` повторов подряд ссылка заканчивается
  (`repeated_page`), повтор не сохраняется. Discovery сравнивает со всеми
  прочитанными страницами, потому что открывает их не по порядку, и читает
  товары даже без `save_items`: иначе магазин, отвечающий последней страницей
  на любой номер, вёл бы поиск до `max_page`. Правило `any` в discovery
  заменяется на `all`: один рекламный товар на каждой странице не означает
  конца каталога. Конвертер переводит поля MVP `wait_for_changing_content`,
  `max_the_same_content_pages`, `stop_if_all_items_the_same` в этот блок.
- **Задачи из discovery.** Итог `discover` превращается в задачи `list` по
  диапазонам страниц `runtime.pages_per_task` — без страниц, уже сохранённых
  для этой ссылки (у ссылок с другой сортировкой порядок товаров другой, им
  нужны все страницы). Блок и неопределённость
  обрабатываются политиками `on_blocked` / `on_unknown` (`skip_link`,
  `fallback_first_chunk`, `fallback_config_limit`, `fail_run`). Задача `list`
  с диапазоном проходит страницы `start_page…last_page` по шаблону адреса.
- **Пороги запуска.** После network check парсер, у которого здоровых
  (неоткрытых) прокси меньше `min_healthy_per_scraper` или доли
  `min_healthy_ratio_per_scraper`, закрывается воротами; если по всем
  прокси run меньше `min_healthy_total` / `min_healthy_ratio` — run падает до
  запуска браузеров.
- **Отметка о прогреве профиля.** В режиме `persistent` прогрев (`warmup_urls`)
  и bootstrap пакета записываются в профиль с версией и временем; следующий
  слот на том же профиле пропускает их, пока отметка моложе
  `profiles.bootstrap_ttl_seconds`.

## Последствия

- Ни одного глобального барьера: парсер A парсит, пока B на probe или discovery.
- Состояние ворот восстанавливается из задач в хранилище (есть ли успешный
  `probe`), поэтому resume (этап 8) не повторяет пройденную проверку.
- Сайты с пагинацией только кнопкой «дальше» остаются одной задачей на ссылку.
- Первая страница задачи с диапазоном не с чем сравнить: если магазин отвечает
  последней страницей за концом каталога, задача `[N, 0]` после неизвестного
  конца может сохранить одну такую страницу лишний раз. Дубли между задачами —
  отдельный будущий шаг итоговой сборки: убирать строки с одинаковым ключом
  товара.

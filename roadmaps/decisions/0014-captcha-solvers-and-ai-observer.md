# 0014. Решение капч через API и ИИ-наблюдатель

Статус: принято (2026-10-28)

## Контекст

- Часть сайтов показывает капчу; кроме ручного решения нужны внешние сервисы
  решения капч по API.
- Вёрстка сайтов меняется, и значительная доля поломок парсинга — мелкие
  правки селекторов в `scraper.json`. Планируется ИИ-наблюдатель, который
  разбирает логи и события, находит такие поломки и предлагает исправления.
- Ошибочная автоматическая правка пакета может испортить данные сразу во всех
  прогонах, поэтому изменения должны проходить проверку до применения.

## Решение

### Решение капч

- `CaptchaSolver` — интерфейс: на вход описание капчи на странице (тип, ключ
  сайта, адрес, изображение), на выход — решение или отказ с категорией.
  Реализации для конкретных сервисов — подключаемые адаптеры с собственными
  настройками; ключи API — только из переменных окружения.
- Решатель вызывается из точки ручного вмешательства `StateWaiter`: при
  состоянии `captcha` цепочка «решатель → ручное решение → отказ» настраивается
  на парсер. После решения состояние страницы определяется заново по живому DOM.
- Стоимость, время и исход каждого решения записываются в события; лимиты
  расходов задаются на run и на парсер.
- **Ручное решение — первым.** Пока автоматических решателей нет, капча решается
  человеком: слот держит страницу открытой, отправляет уведомление (почта,
  Telegram) со ссылкой на запуск, парсер и адрес, и ждёт решения в пределах
  таймаута, проверяя страницу. Dispatcher и watchdog видят состояние «ждёт
  вмешательства» и не считают слот зависшим. Для ручного решения браузер
  должен быть видимым на машине (или доступным удалённо).
- Решатели через сервисы и через ИИ-модели — реализации того же
  `CaptchaSolver`; они встают в цепочку перед ручным решением без изменения
  исполнителей.
- Уведомления — адаптеры получателей с общим интерфейсом (почта, Telegram;
  позже другие мессенджеры); ими же пользуются итоги запусков.

### ИИ-наблюдатель

- Наблюдатель — отдельный компонент вне ядра со своими зависимостями. Ядро не
  импортирует его и не зависит от поставщика модели.
- Ядро даёт наблюдателю только публичные интерфейсы:
  - поток структурированных событий (исходы задач, категории ошибок, причины
    `PageOutcome`, пропущенные обязательные поля);
  - снимки страниц при ошибках (HTML, по возможности скриншот) в хранилище
    артефактов;
  - версии пакетов парсеров;
  - API предложений изменений.
- Наблюдатель не правит файлы напрямую: он создаёт **предложение** —
  изменение `scraper.json` с обоснованием. Предложение проходит проверку:
  схема v3, компиляция шаблонов, повтор извлечения на сохранённых снимках и
  контрольный прогон на нескольких адресах. Применение — по политике парсера:
  только человеком или автоматически после проверки, с новой версией пакета и
  возможностью отката.
- Код пакетов (`actions.py`, `pipeline.py`) наблюдатель может только предлагать,
  автоматически он не применяется.

## Последствия

- Уже на этапах хранилища и параллельности закладываются структурированные
  события с версией схемы, снимки страниц при ошибках и версия пакета в каждой
  попытке.
- Пакеты парсеров версионируются; результат каждой попытки связан с версией
  пакета, по которой он получен.
- Расходы на решение капч и работа наблюдателя видны в событиях и итогах run.

# 0015. Открытое ядро, ресурсный профиль, запуски и доставка результатов

Статус: принято (2026-10-28), уточняет [0013](0013-scaling-and-replaceable-backends.md)

## Контекст

- Ядро распространяется как открытая библиотека: любой может бесплатно
  развернуть её у себя, подключить свои прокси и запускать парсеры из командной
  строки. Облачная обвязка (кабинеты клиентов, их прокси и лимиты), ИИ-наблюдатель
  и подобные надстройки развиваются вне этого репозитория.
- Основной сценарий сейчас — один владелец и один клиент на одной машине. Другие
  клиенты и несколько машин — будущее, к которому нужен фундамент, но не
  реализация.
- Типичная машина небольшая: 8–16 ГБ памяти и 2–4 ядра, на ней должны
  одновременно работать 10–15 сайтов.
- Пользователю нужны запуски и их история (открыть вчерашний результат);
  аналитика вроде отслеживания цен появится позже.
- Результаты нужно отправлять по-разному: файлы разных форматов, архивы,
  веб-хранилища, почта, мессенджеры.

## Решение

### Границы ядра

- `dailyscraper` — библиотека и CLI. Сервисы `app/` — единственная точка входа
  для CLI, будущего HTTP API и внешних обвязок.
- HTTP API и веб-интерфейс — необязательные части поверх сервисов `app/`
  (отдельный пакет или дополнительная зависимость), не в ядре.
- Развёртывание из коробки: официальный Docker-образ и шаблон развёртывания
  (конфигурация по умолчанию, папка парсеров, запуск через CLI; веб-интерфейс —
  по желанию).
- Ядро не реализует клиентов, кабинеты и биллинг. Фундамент для них: каждый run,
  задача, событие и артефакт несут `project_id` (по умолчанию `default`).

### Ресурсный профиль

- Целевой профиль: 10–15 одновременных сайтов на машине с 8 ГБ памяти и
  2 ядрами — с разумными настройками по умолчанию, без ручной оптимизации.
- `BrowserManager` запускает новый браузерный слот только при наличии бюджета
  памяти (резерв задаётся в настройках, по умолчанию оценивается по объёму
  памяти машины); иначе задача ждёт освобождения.
- Блокировка тяжёлых ресурсов (изображения, шрифты, медиа) включена по умолчанию
  для браузерных парсеров и отключается в пакете.
- HTTP-транспорт предпочтителен, когда сайт это позволяет: HTTP-слот в десятки
  раз дешевле браузерного.
- Профиль проверяется тестом длительной работы в контейнере с ограничением
  памяти и процессора.

### Запуски и история

- Каждый запуск хранится со статусом, временем, снимком настроек, версиями
  пакетов, итогами и файлами результатов; CLI показывает список запусков и
  открывает результаты любого из них. Срок хранения задаёт retention.
- Каждая строка результата получает стабильный ключ товара (`item_key`) из
  `identity_fields` пакета или ссылки на detail. По нему позже строятся история
  и сравнение запусков без изменения хранения.

### Доставка результатов

- После финализации запуска результаты отправляются по списку доставок из
  настроек: форматы (CSV, JSON, XLSX, XML), архив, получатель (локальная папка,
  веб-хранилище, почта, мессенджер) и условие (успех, любой исход).
- Получатель — адаптер с общим интерфейсом. Сбой доставки повторяется и
  записывается в события, но не меняет результат запуска и не теряет файлы.
- На этапе хранилища — локальные файлы и архив; остальные получатели — позже.

### Версии пакетов

- Версия пакета — хэш содержимого (`scraper.json` и `.py`), вычисляется при
  загрузке; необязательный номер версии в `scraper.json` — для людей.

### Секреты и события

- Секреты (учётные данные прокси, ключи сервисов, пароли сайтов) — только из
  переменных окружения и `.env`; в событиях и логах маскируются.
- События — структурированные JSON с версией схемы; консоль, итоги и метрики
  строятся из них.

## Последствия

- Приоритет — работающий сервис для одного владельца на одной машине. Клиенты,
  веб-интерфейс, несколько машин и аналитика добавляются поверх без переделки
  хранения и протоколов.
- Схема хранилища этапа 3 включает `project_id`, историю запусков, `item_key`,
  версию пакета в попытке и записи доставок.

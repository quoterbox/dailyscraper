# 0002. Синхронный Dispatcher, браузеры в процессах-слотах

Статус: принято (2026-10-22)

## Контекст

Ранний целевой документ MVP предлагал async-first ядро на `asyncio`. При этом:

- проверенная инфраструктура MVP (store, leases, команды, recovery) синхронная;
- каждый браузер должен жить в отдельном процессе, чтобы зависший Chromium можно
  было убить снаружи; родитель только ждёт сообщений от процессов;
- `sqlite3` синхронный, async-слой над ним добавляет сложность без выигрыша.

## Решение

- Родительский процесс — один поток, `Dispatcher` с циклом событий поверх
  `multiprocessing.connection.wait`. Только он решает порядок задач, выбор
  прокси, выделение браузера и retry, и только он пишет в SQLite.
- Браузеры — долгоживущие процессы-слоты (`multiprocessing.Process`, spawn), один
  Chromium на пару `(site, proxy)`, много задач подряд. Слот можно убить
  отдельно, вместе с деревом процессов.
- Async допускается **внутри** слота, когда он реально нужен: HTTP-слот с
  `httpx`, несколько вкладок на браузер. Протокол «родитель ↔ слот» от этого не
  меняется.

## Последствия

- `ProcessPoolExecutor` не используется: он не позволяет убить один процесс без
  поломки всего пула.
- Dispatcher изолирован за интерфейсом, поэтому позже его можно заменить на
  asyncio без изменения контрактов `TaskQueue`, `ProxyManager`, `BrowserManager`.
- HTTP-транспорт и FastAPI откладываются (этап 8+). API-режим парсеров работает
  через запросы браузера в hooks пакета, как в MVP.

# 0010. Загрузка настроек без Dynaconf

Статус: принято (2026-10-22)

## Контекст

Предшественники загружают настройки через Dynaconf: глобальный объект,
шаблоны `@format {this.BASE_PATH}`/`{env[...]}`, переопределения `ENV_DS_*`,
ленивые вычисления. Объект изменяемый, поэтому дочерние процессы и тесты
легко получают не тот снимок, а импорт модуля настроек сам по себе читает
файлы.

## Решение

- `load_settings(project_root)` — явная функция, глобального объекта нет.
  Результат — неизменяемая pydantic-модель `Settings`; неизвестные секции —
  ошибка.
- Источники в порядке приоритета (последний побеждает):
  1. `config/<env>/*.json` по алфавиту;
  2. `config/<env>/*.local.json` (не в git);
  3. в testing — каталог `DAILYSCRAPER_TEST_CONFIG_ROOT` внутри тестовой
     рабочей папки;
  4. переменные `DAILYSCRAPER__SECTION__KEY=value` (значение разбирается как
     JSON, иначе строка).
- Строки `${env:NAME}` подставляются из окружения процесса и файла `.env`
  (`.test.env` в testing); окружение процесса приоритетнее. Отсутствующая
  переменная — ошибка.
- Относительные пути разрешаются от корня проекта. В testing каталоги данных и
  логов обязаны лежать внутри тестовой рабочей папки, иначе загрузка падает.
- Секции добавляются по мере появления потребителей: на этапе 1 — `paths` и
  `scrapers`.

## Последствия

- Дочерним процессам передаётся готовый снимок (`model_dump`), они не читают
  конфиг с диска.
- Тесты изолированы: `tests/bootstrap.py` удаляет унаследованные
  `DAILYSCRAPER_*` переменные, а загрузчик не даёт писать вне рабочей папки.

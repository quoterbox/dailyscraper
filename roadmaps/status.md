## Текущий этап: 5 — прокси

Готово, ожидает коммита владельцем. Этап 4 (параллельность, лимиты сессий,
ADR 0016) закоммичен.

### Сделано

- `proxies/sources.py`: пул из `static`/`gateway`/`api` (схема v2 MVP), стабильные
  `ProxyId`, сессии gateway с `generation` в логине, порты из `port_range`,
  API с `items_field`/`field_map`, ошибками провайдера в ответе 200, запасным
  статичным списком и скрытием ключа в URL.
- `proxies/health.py`: circuit breaker MVP по `(site, ProxyId)` в хранилище
  (миграция 3, `proxy_health`, атомарное изменение): мгновенное открытие для
  блока, капчи и 407, по порогу — для тайм-аутов и сетевых ошибок, растущий
  cooldown и half-open, новая генерация вместо отдыха для сессий gateway.
- `proxies/allocator.py`: порядок прокси для новой сессии сайта, `avoid` задачи,
  текущая генерация сессии.
- `proxies/network_check.py`: проверка через каждую прокси перед запуском,
  параллельно; не прошедшие открываются для сайтов запуска.
- `transport/`: прокси для `ephemeral` (авторизация Playwright), профиль и
  MV3-расширение для `persistent` с проверкой применения прокси до первой
  навигации, очистка профиля при смене идентичности прокси, блокировка
  изображений, медиа и шрифтов.
- `BrowserManager` выбирает прокси через `ProxyAllocator` и лимиты; слот живёт с
  одной прокси, ротация по `slot_max_tasks`/`slot_max_age_seconds`.
- `Dispatcher` сообщает здоровью итог каждой попытки, закрывает слот при
  открытии circuit, повтор задачи обходит упавшую прокси; события
  `proxy.checked`, `proxy.health`; в итогах — попытки по прокси.
- Исправление: `classify_error` считал `HTTPError` urllib ошибкой файловой
  системы.
- Тестовый прокси (`tests/harness/connect_proxy.py`) умеет требовать логин и
  пароль, пропускать обычные HTTP-запросы и вести журнал туннелей.
- ADR [0017](decisions/0017-proxies.md).

### Не входит в этап 5

- Пороги блокировки запуска по доле здоровых прокси и пробный прогон парсера —
  этап 6 (ворота).
- Ротация сессии gateway по времени — сейчас TTL сессии задаёт провайдер в
  шаблоне логина (`_ttl_30m`), генерация меняется при открытии circuit.

## Решения после этапа 2

- ADR [0012](decisions/0012-transports-isolation-and-sync-core.md): транспорт за
  узким интерфейсом (Playwright и HTTP), HTTP-транспорт — этап 4a, режимы
  изоляции браузера `persistent` / `ephemeral` / `shared`, синхронное ядро и
  async-фасад для встраивания.
- ADR [0013](decisions/0013-scaling-and-replaceable-backends.md): дорожки
  HTTP-слота, `max_parallel` парсера, пакетные отметки, нагрузочные тесты;
  хранилище за интерфейсами с контрактными тестами (PostgreSQL, Redis, S3 —
  адаптерами), сериализуемый протокол слота, идемпотентность, `host_id`;
  координатор и агенты хостов — этап 10.
- ADR [0014](decisions/0014-captcha-solvers-and-ai-observer.md): ручное решение
  капчи с уведомлением на почту и в Telegram — этап 4b; автоматические решатели
  (сервисы, ИИ) — этап 6a в той же цепочке; ИИ-наблюдатель вне ядра с
  проверяемыми предложениями изменений `scraper.json` — этап 9.
- ADR [0015](decisions/0015-open-core-resources-and-runs.md): ядро — открытая
  библиотека с CLI; HTTP API и веб-интерфейс — поверх `app/`, вне ядра;
  ресурсный профиль 10–15 сайтов на 8 ГБ и 2 ядрах; история запусков,
  `item_key`, версия пакета — хэш; доставка через адаптеры получателей;
  `project_id`; Docker-образ и шаблон развёртывания — этап 8.
- Ближайшая цель — работающий сервис для одного владельца на одной машине
  (этапы 3–7).
